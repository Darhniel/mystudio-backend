# Cloudinary image hosting

Studio and equipment images are stored in Cloudinary; PostgreSQL keeps only the
returned `secure_url` and `public_id`. The API never proxies image bytes after
the upload request and never stores files on the application server.

## Configuration

Required in every environment that uploads images:

```dotenv
CLOUDINARY_CLOUD_NAME=...
CLOUDINARY_API_KEY=...
CLOUDINARY_API_SECRET=...
```

Optional:

```dotenv
# Default: 5 MB (5 * 1024 * 1024)
IMAGE_UPLOAD_MAX_BYTES=5242880
```

Development reads these from `.env`. Production reads only process environment
variables and **fails to start** if any of the three credentials are missing.

The application configures the official SDK lazily, on the first upload or
deletion. Importing the codebase never requires credentials, which keeps
management commands and tests runnable without a Cloudinary account.

## Folders

| App | Cloudinary folder |
|---|---|
| Studios | `mystudio/studios` |
| Equipment | `mystudio/equipment` |

The folder constants live in `apps/studios/services.py` and
`apps/equipment/services.py`. Public IDs are generated by Cloudinary; client
filenames are not trusted.

## Validation

`apps.common.cloudinary.validate_image_file()` runs before any provider call:

- accepts **JPEG**, **PNG** and **WebP**;
- rejects everything else, including GIF and SVG;
- opens the bytes with Pillow and calls `verify()`, so a renamed `.jpg` text
  file is rejected even when its extension and content type look valid;
- rejects files larger than `IMAGE_UPLOAD_MAX_BYTES` (5 MB by default).

Validation raises Django `ValidationError` with an `image` key, which the shared
API exception handler renders as `400`.

## Services

Cloudinary access is never placed in views.

### Studios — `apps/studios/services.py`

- `add_studio_image(studio, image, alt_text="", display_order=None)` uploads
  first, then inserts the row. A failed insert destroys the fresh asset.
  Omitting `display_order` appends to the end of the studio's images.
- `update_studio_image(image, alt_text=None, display_order=None)` changes
  metadata without re-uploading.
- `delete_studio_image(image)` removes the PostgreSQL row and its Cloudinary
  asset atomically inside a single database transaction. If the Cloudinary
  deletion fails, the row deletion is rolled back and the image stays visible.
  This prevents orphaned Cloudinary assets. A provider failure returns `502`
  (or `503` when unconfigured) and the image is unchanged.

### Equipment — `apps/equipment/services.py`

- `set_equipment_image(equipment, image)` uploads and saves the new references,
  then attempts to remove the replaced asset. If the database write fails, the
  new upload is destroyed. A failure to delete the previous asset is logged and
  does not fail the replacement, because the new image is already active.
- `remove_equipment_image(equipment)` clears the row and deletes the Cloudinary
  asset in one transaction. If the provider deletion fails, the row clearing is
  rolled back and the image stays visible. This prevents orphaned Cloudinary
  assets. A provider failure returns `502` (or `503` when unconfigured) and the
  image is unchanged. The operation is idempotent when no image exists.

## API

All image endpoints require a Bearer token and the `owner` or `manager` role
(`staff` is read-only and receives `403`).

| Method | Path | Notes |
|---|---|---|
| POST | `/api/v1/studios/{slug}/images/` | `multipart/form-data`: `image`, optional `alt_text`, `display_order` |
| PATCH | `/api/v1/studios/{slug}/images/{image_id}/` | JSON: `alt_text` and/or `display_order` |
| DELETE | `/api/v1/studios/{slug}/images/{image_id}/` | Deletes row + Cloudinary asset |
| POST | `/api/v1/admin/studios/{id}/images/` | Administrative upload, same fields as above |
| PATCH | `/api/v1/admin/studios/{id}/images/{image_id}/` | JSON: `alt_text` and/or `display_order` |
| DELETE | `/api/v1/admin/studios/{id}/images/{image_id}/` | Deletes row + Cloudinary asset |
| POST / PUT | `/api/v1/equipment/{equipment_id}/image/` | `multipart/form-data`: `image`; replaces any existing image |
| DELETE | `/api/v1/equipment/{equipment_id}/image/` | Clears row + Cloudinary asset |
| POST | `/api/v1/admin/equipment/` | `multipart/form-data` with optional `image` |
| PATCH | `/api/v1/admin/equipment/{id}/` | Multipart `image` replaces; JSON `remove_image: true` clears |

Example:

```powershell
curl.exe -X POST "http://127.0.0.1:8000/api/v1/studios/natural-light/images/" `
  -H "Authorization: Bearer $TOKEN" `
  -F "image=@studio.jpg" `
  -F "alt_text=White cyclorama" `
  -F "display_order=0"
```

Failure responses:

| Status | Meaning |
|---|---|
| `400` | Invalid type, corrupt image or file over 5 MB |
| `401` | Missing or invalid token |
| `403` | Authenticated but not an owner/manager |
| `404` | Studio/image/equipment not found (images are scoped to their studio) |
| `502` | Cloudinary rejected an upload or deletion |
| `503` | Cloudinary credentials are not configured |

Provider details and credentials are never included in responses or logs. The
shared log filter already masks `CLOUDINARY_API_SECRET` and any `api_key=`
assignment.

## Tests

Tests generate real in-memory JPEG/PNG/WebP files with Pillow and mock
`cloudinary.uploader.upload` / `destroy`. No network access or credentials are
required. Run:

```powershell
python -m pytest apps/common/tests/test_cloudinary.py `
  apps/studios/tests/test_image_services.py `
  apps/equipment/tests/test_image_services.py `
  apps/studios/tests/test_api.py `
  apps/equipment/tests/test_api.py
```
